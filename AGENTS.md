# AGENTS.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`External Rename Handler` is an Obsidian plugin that recognizes renames made outside of Obsidian (e.g. from the OS file explorer or another app) and reports them to Obsidian as real renames, so the file keeps its identity instead of arriving as an unrelated delete plus create. It is built on `@mnaoumov/obsidian-lib`, with tooling from `@mnaoumov/obsidian-dev-toolkit` and `@mnaoumov/typescript-dev-toolkit`.

Since **4.0.0** it does **not** rewrite links itself. Rename and delete handling — the `RenameDeleteHandlerComponent` this plugin used to construct — belongs to the separate **`Advanced Rename and Delete Handler`** plugin (`advanced-rename-and-delete-handler`), which owns it for the whole vault; four sibling plugins made the same handover. This plugin suggests installing it and offers its legacy `shouldUpdateLinks` value across through that plugin's `migrateSettings` API.

## Architecture

- **Root config files** are thin re-exports — actual logic lives in `scripts/` (`eslint.config.mts` → `scripts/eslint-config.ts`, `commitlint.config.ts` → `scripts/commitlint-config.ts`, etc.).
- **`src/`** — plugin source:
  - `main.ts` — Obsidian entry point (default-exports the `Plugin` class from `plugin.ts`)
  - `plugin.ts` — `Plugin` extends `PluginBase`; in `onloadImpl` wires up the settings component/tab, the `obsidian-lib` `PluginSuggestionComponent` (suggesting `Advanced Rename and Delete Handler`), the `ExternalRenameHandlerComponent`, and the `obsidian-lib` `SettingsMigrationComponent`; asserts the vault adapter is a `FileSystemAdapter`. It constructs **no** `RenameDeleteHandlerComponent` — two handlers acting on one rename corrupt links, and the suggested plugin is the vault's single owner
  - `desktop-external-rename-handler-component.ts` — core `LayoutReadyComponent`; builds/cleans the path↔inode map on layout ready, starts the `chokidar` watcher on the vault dir, and translates filesystem add/unlink events into Obsidian rename/delete handling (with a configurable deletion-vs-rename timeout). A `change` refreshes the map when its inode differs from the stored one: a save that renames a temp file over the note gives it a new inode, which `atomic: true` reports as a `change`, and a stale entry read the note's next external rename as a delete plus a create on every file system measured. The startup pass still trusts a cached path with a birth time, so such a save made while Obsidian was closed stays unseen until the note's next live change. So does one renamed away within the same polling interval, since the polling backend then never stats the replaced file at its old path. The watcher is started directly on layout ready — the `loadSettings` / `saveSettings` handlers only re-register it when the polling interval changes, because the settings are already loaded by the time the layout is ready and the initial `loadSettings` event has therefore been missed. **The `desktop-` prefix is load-bearing, not descriptive** — `obsidian-dev-toolkit`'s shared ESLint config exempts `src/**/desktop-*.ts` from `import-x/no-nodejs-modules` and `obsidianmd/no-nodejs-modules`, which is what lets this file import `node:fs` and `node:fs/promises` with no disable comment. Rename it without the prefix and both rules report again, and the `obsidianmd` twin cannot be waived at all, because the community-directory runner sets `eslint-comments/no-restricted-disable` over `obsidianmd/*`. This plugin is `isDesktopOnly` as a whole, so the prefix names a property of the plugin rather than of the file; the alternative — teaching the shared config to read the manifest flag — was weighed and rejected, to keep one exemption axis rather than two. `onLayoutReady` **disposes the `PathInoMap` it is about to replace and registers the new one via `ComponentEx.registerDisposable`**, and both halves are needed: a reload of this component registers a *second* workspace layout-ready callback, so the method can run again over a map that already owns an open connection and an armed flush, and without the registration nothing closes the connection on unload at all. **Two path forms, never mixed:** Obsidian keys the vault, `adapter.files` and this map by `normalizePath` (NFC, NBSP → space), while the disk and `chokidar` carry the real name, which may be decomposed (NFD). So a startup `stat` goes through `getFullPath(file.path)`, never `getFullRealPath` (a bare join that expects an already-real path). A watcher event is keyed by `normalizePath(path)` and hands the real path to the original `onFileChange`, which normalizes it itself. Mixing them is GH #5: one file-not-found error per decomposed name at startup, and an external rename of such a file read as a delete plus a create. **Renames made while Obsidian was closed** are found in the same startup pass: a loaded file at a path the map does not know, whose inode the map holds under a path now gone from the vault and whose birth time equals the stored one, is an offline rename. They are reported only after the watcher has started and `ensureMetadataCacheReady` has returned, as `vault.trigger('rename', file, oldPath)` — the very shape a live external rename reaches `Advanced Rename and Delete Handler` in (the file already at its new path), which is why that plugin needs nothing new. Read in the deobfuscated app, this is safe because Obsidian builds the vault from disk afresh (the old path never existed for it, so no event of its own fires), `MetadataCache.initialize` drops the old path's cache entry before the cache reports clean, and `MetadataCache.onRename` is idempotent for a file already at its new path (`uniqueFileLookup.add` skips a duplicate). The birth time guards against ext4-style inode reuse, and the live `add` applies the same guard: an `add` whose inode the map holds under another path with a different stored birth time is a create, and the old path's deletion is reported there and then, because the map no longer leads the pending deletion timeout back to it (reuse within the same millisecond still passes as a rename). It is stored as **whole milliseconds** (`toBirthtimeMs`), because a bigint `birthtimeMs` from a Windows directory scan is truncated while plain `stat` carries a fraction, and the two must compare equal. A cached path with no stored birth time (recorded before 4.1.0) is stat-ed once more to backfill it. The `shouldDetectOfflineRenames` setting gates only the event, never the map bookkeeping. `offline-rename.desktop.integration.test.ts` stands in for a restart by disabling the plugin around an on-disk rename: with the patch gone Obsidian's own watcher reduces it to a delete plus a create, which is exactly what a restart leaves
  - `desktop-chokidar-watch.ts` — the `watch` the component uses: `chokidar`'s `FSWatcher` constructed with a scheduler on Node's own `node:timers`. **`chokidar` 6's default scheduler arms its timers with the global `setTimeout` and calls `unref()` on the handle, and in the app's renderer that global is the DOM one, whose handle is a number** — every directory subscription then fails with `timer.unref is not a function` and the watcher reports nothing, with no error in the console unless something listens to the watcher's `error`. Plain Node never shows it, so a probe outside the app proves nothing about this. Three more `chokidar` 6 facts the component's options rest on, each found by driving the real binary: it **throws on a `pollingInterval` of `0` whatever the backend**, so the polling intervals are passed to the `polling` backend only (a disabled polling setting otherwise left no watcher at all after a settings save); on Windows an **`add` from a directory scan carries `BigIntStats`, so a bigint `stats.ino`**, on either backend (the raw `readdirp` stats reach the listener), which the handler converts with `Number()` before the map lookup (it rounds the same way plain `stat` does, verified on inodes above 2^53); and it calls **`ignored` with absolute paths** and with the vault's ancestors, so the predicate judges only the part inside the vault. `engines.node` says `>= 22.22`, while installers from 1.5.8 (the oldest the plugin's `minAppVersion` accepts) through 1.12.x ship Node 18.18 to 22.21; the floor is declared rather than needed — chokidar 6 and readdirp 5 use no API newer than Node 18, and the rename event sequence was re-checked on Node 18.18 and 22.21 on both backends
  - `path-ino-map.ts` — `PathInoMap`, a two-way path↔inode map persisted in IndexedDB (debounced writes) to detect renames across sessions, with each path's birth time kept beside it (`birthtimeMs`, absent from entries written before 4.1.0 and then reported as unknown, never as `0`; no DB version bump, since the store is keyed by path and takes the extra field). Three lifetime facts, all of them load-bearing and each one a defect that was live until 4.0.1: it opens on **`window`, never `activeWindow`** — the store is keyed by `app.appId` so it belongs to the vault, and binding it to a focused popout means closing that popout closes the connection under a still-loaded plugin; it implements **`Disposable`**, and `[Symbol.dispose]` cancels the debouncer, *flushes* what is queued and closes the connection, because a cancel alone still drops the pending writes; and `processStoreActions` drops the queued actions **only after `commit()` returns**, reporting a failure through `printError` instead of letting it escape the debounce callback as an uncaught error. The component is what ties that teardown to a lifetime — see the entry below
  - `dot-file.ts` — `isDotFile` helper (treats any path segment starting with `.` as a dot file to ignore)
  - `plugin-settings.ts` — `PluginSettings` data class (`pollingIntervalInMilliseconds`, `deletionRenameDetectionTimeoutInMilliseconds`, `shouldDetectOfflineRenames`, plus two handover bookkeeping keys: `isAdvancedRenameAndDeleteHandlerSuggestionDeclined` and `proposedShouldHandleRenames`, the pending offer — `null` means nothing to offer, which is also what a fresh install has)
  - `plugin-settings-component.ts` — `PluginSettingsComponent` extending the `obsidian-lib` `PluginSettingsComponentBase`; its legacy-settings converter is what carries a pre-4.0.0 `shouldUpdateLinks` into `proposedShouldHandleRenames` before the first save rebuilds `data.json` from the declared properties alone
  - the settings handover itself is the `obsidian-lib` `SettingsMigrationComponent`, constructed in `plugin.ts`: it watches for `Advanced Rename and Delete Handler`'s `^1` API and offers the pending value through its `migrateSettings`. This plugin supplies only the two closures — `getProposedSettings`, which wraps `proposedShouldHandleRenames` into a payload (and returns `null` when nothing is pending), and `retireProposedSettings`. Two things the shared component guarantees, both originally found by driving the real binary and each worth knowing before anyone reaches for a hand-rolled variant again: it never gates the watch on the pending value in `onload` (the settings component is a sibling still loading, so `settings` holds the defaults there — it wires the api-ref `change` and the `loadSettings` edges and re-reads inside the propose path), and this plugin's `retireProposedSettings` must use `editAndSave`, never `setProperty`, so the retirement outlives a reload
  - `advanced-rename-and-delete-handler.ts` — the suggested plugin's id and display name, written once and shared by the suggestion and the migration, plus `MigratableSettings`, the payload half of the handover contract (its envelope — `migrateSettings`, the proposer, the applied flag — comes from `obsidian-lib`'s `settings-migration-api`)
  - `plugin-settings-tab.ts` — `PluginSettingsTab` rendering the settings UI via `SettingEx`
  - `patches/file-system-adapter-on-file-change-patch-component.ts` — `MonkeyAroundComponent` that patches `FileSystemAdapter.onFileChange` to suppress Obsidian's own notifications for everything except dot files (dot files still fall through to the original), and to capture the original method for the handler to invoke. Because this suppression is unconditional, the `chokidar` watcher is the *only* thing left that reaches the UI — if it fails to start, no external change is ever reflected
- **`main` field** points to `src/main.ts` (Obsidian plugin source entry; built artifact is `dist/build/main.js`, not published to npm).
